How I built NetworkDays

I spent roughly three months turning a focused HubSpot workflow problem into a production app with real billing, deployment controls, observability, and 552 automated tests.

Built and operated by Sharoze Iftikhar

The product started with one precise job

NetworkDays calculates business days inside HubSpot workflows. It skips weekends and public holidays, with support for more than 145 country holiday calendars. The product is deliberately focused on bringing that business-day logic into HubSpot workflow actions.

The app is available through direct HubSpot OAuth installation today. It is not yet listed on the public HubSpot Marketplace because I am still working toward the required unaffiliated-install threshold. I built the product and its operating systems for real production use before that distribution milestone.

I kept the architecture understandable

The backend runs on Python and FastAPI. Data lives in SQLite with WAL mode. The application is containerized with Docker and deployed on Hetzner, with a dedicated production server and a separate shared sandbox and development box. Caddy handles TLS and reverse proxy duties.

HubSpot OAuth manages installation and account access. HubSpot UI Extensions provide the in-app interface. Production runs on its dedicated server, while sandbox and development work stay on the separate shared box.

The test count matters because the failure modes are real

The latest release has 552 automated tests. Testing was one part of the release discipline, alongside independent audits, database snapshots, and rollback tags.

I also ran two independent AI-model audits across security and billing integrity. Two different model families cross-checked each other's findings. The audits caught real bugs before they reached a paying customer, including one that would have silently downgraded every subscriber back to the free tier roughly a month after signup.

That finding justified the discipline. The point of using AI in review was not to replace tests or judgment. It was to create another independent path for finding faults in code where a quiet error could affect every subscriber.

Production changes start with a way back

Every production deployment is gated on two steps first: a database snapshot and a git rollback tag. There are no exceptions. A deploy is not ready if I cannot restore the data and identify the exact code state that preceded it.

Paddle billing went live only after checkout, webhooks, automatic dunning and retry handling, and a daily reconciliation sweep were verified end to end in production. The daily reconciliation sweep checks for missed webhook events.

The observability layer covers error tracking, scheduler heartbeats, uptime monitoring, and a metrics dashboard with alerting. These systems answer different questions: whether the app is reachable, whether background work is still running, whether exceptions are occurring, and whether operating metrics have moved outside expected conditions.

The final test is ordinary production use

NetworkDays has one real paying-adjacent customer using it in production today, a company in Brazil. It is not a hypothetical account and not a demo environment.

Roughly three months of active work produced more than a workflow action. The result is a production app with tiered access, billing controls, safe releases, monitoring, and an interface inside HubSpot. The build is still moving toward public Marketplace eligibility, but the engineering discipline is already in place.
